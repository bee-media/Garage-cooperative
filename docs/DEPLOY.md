# Развёртывание и автодеплой «ГСК Родник»

Два сервера (тестовый и боевой) на чистом Debian. Приложение работает как systemd-сервис (без Docker), снаружи его выставляет Nginx Proxy Manager. Выкатка — автоматически из вашего приватного GitLab.

## 1. Как всё устроено

```
Интернет ──► Nginx Proxy Manager (TLS, домены) ──► nginx на сервере ГСК ──► Node.js API ──► PostgreSQL
                  :443                              :8081  сайт жителей (PWA)    :3000      :5432
                                                    :8082  портал правления      (только 127.0.0.1)
                                                    /api/ → API
```

| Что | Где на сервере |
|---|---|
| Выкаченные версии | `/opt/gsk/releases/<дата-время>-<коммит>/`, активная — ссылка `/opt/gsk/current` |
| Скрипты | `/opt/gsk/bin/` (`deploy-receive.sh`, `backup.sh`, `restore.sh`, `seed.sh`) |
| Секреты и настройки | `/etc/gsk/api.env` (права 640, `root:gsk`) |
| Фото и файлы жителей | `/var/lib/gsk/storage` (вне каталога приложения, переживает деплой) |
| Резервные копии | `/var/backups/gsk/db` (дампы), `/var/backups/gsk/files` (снимки файлов) |
| Журнал API | `journalctl -u gsk-api -f` |

Пользователи: **`gsk`** — под ним работает API (вход запрещён); **`gsk-deploy`** — принимает релизы от GitLab. Ключ CI привязан к одной команде (`deploy-receive.sh`): им нельзя открыть терминал, скопировать файлы или выполнить что-то ещё. Деплой может только перезапустить `gsk-api` (правило sudo).

**Как идёт выкатка:** GitLab собирает приложения → упаковывает `release.tar.gz` → по SSH передаёт на сервер → сервер распаковывает, ставит зависимости, делает копию базы, применяет миграции, переключает ссылку `current`, перезапускает API и проверяет `/api/health`. Если проверка не прошла — **автоматически возвращается предыдущая версия**, а задача в GitLab краснеет.

**Ветки:**

| Ветка | Что происходит |
|---|---|
| `develop` | сборка и **автоматический** деплой на тестовый сервер |
| `main` | сборка и деплой на боевой по кнопке **Run** (ручной запуск) |
| прочие / merge request | только проверка сборки |

Рабочий процесс: фича → merge request в `develop` → тест на тестовом сервере → merge `develop` в `main` → кнопка деплоя на боевой.

## 2. Что понадобится

- Два сервера Debian 12 или 13 (тест и бой), доступ по SSH с sudo, выход в интернет (apt, npm).
- Четыре домена или поддомена (по два на сервер): сайт жителей и портал правления. Пример:

| | Тест | Бой |
|---|---|---|
| Жители (PWA) | `test.rodnik.example.ru` | `rodnik.example.ru` |
| Правление (портал) | `test-admin.rodnik.example.ru` | `admin.rodnik.example.ru` |

- Nginx Proxy Manager с возможностью выпускать/загружать сертификаты.
- GitLab с Runner (executor **Docker**, образы `node:22-bookworm` и `alpine:3.20` должны скачиваться).

> **Безопасность входа.** Для сотрудников правления включена двухфакторная защита (код из приложения на телефоне): без неё работать в системе нельзя. Дополнительно портал можно закрыть списком доступа в Nginx Proxy Manager — см. шаг 4.4.

## 3. Подготовка сервера (делается один раз на каждый сервер)

### 3.1. Ключ для GitLab CI
На своём компьютере (по ключу **на каждый сервер**):

```bash
ssh-keygen -t ed25519 -f gsk-ci-test -C "gitlab-ci-test" -N ""
ssh-keygen -t ed25519 -f gsk-ci-prod -C "gitlab-ci-prod" -N ""
```

`gsk-ci-test.pub` понадобится на шаге 3.3, закрытый `gsk-ci-test` — для GitLab (шаг 5).

### 3.2. Скопировать файлы деплоя на сервер
```bash
scp -r deploy/server user@СЕРВЕР:/tmp/gsk-setup
```

### 3.3. Запустить настройку
На сервере (пример для **тестового**):

```bash
cd /tmp/gsk-setup
sudo bash setup.sh --env test \
  --app-domain test.rodnik.example.ru \
  --admin-domain test-admin.rodnik.example.ru \
  --admin-phone 9001112233 \
  --admin-email chairman@example.ru \
  --deploy-pubkey "$(cat /путь/к/gsk-ci-test.pub)"
```

Если Nginx Proxy Manager стоит на **другой машине**, добавьте `--listen-addr <внутренний IP этого сервера> --npm-ip <IP машины с NPM>`: внутренние сайты будут слушать этот адрес, а брандмауэр пустит на порты 8081/8082 только NPM.

Для боевого — то же с `--env prod` и своими доменами и ключом `gsk-ci-prod.pub`.

Скрипт повторно запускать безопасно: существующие пароли и `api.env` не перезаписываются. Он ставит Node.js 22, PostgreSQL 16, nginx, ufw, fail2ban; создаёт базу, пользователей, ключи VAPID, файл окружения, systemd-юниты, ночной бэкап. В конце печатает **пароль первого администратора — сохраните его**.

Отличие теста от боя: на тестовом сервере `PUSH_DRY_RUN=1` — уведомления **не отправляются** жителям, а пишутся в журнал (чтобы тесты не рассылали настоящие push).

### 3.4. После настройки
- Для push на Android положите ключ Firebase на сервер и включите в `/etc/gsk/api.env` строку `FCM_SERVICE_ACCOUNT_FILE` (подробно — [ANDROID.md](ANDROID.md)).
- Для отправки квитанций на почту впишите в `/etc/gsk/api.env` параметры `SMTP_*` (подробно — [DATA.md](DATA.md)). Пока `SMTP_HOST` пуст, письма не отправляются, а сохраняются в файлы (тестовый режим).
- Рекомендуется запретить вход по паролю в SSH (`PasswordAuthentication no` в `/etc/ssh/sshd_config`) **после** того, как убедились, что вход по ключу работает.

## 4. Nginx Proxy Manager

Для каждого сервера создайте **два** Proxy Host.

### 4.1. Сайт жителей
**Hosts → Proxy Hosts → Add Proxy Host**

| Вкладка | Поле | Значение |
|---|---|---|
| Details | Domain Names | `rodnik.example.ru` |
| | Scheme / Forward Hostname / Port | `http` / IP сервера ГСК / `8081` |
| | Cache Assets | **выключить** (кэширование делает сам сервер) |
| | Block Common Exploits | включить |
| | Websockets Support | можно включить (не требуется) |
| SSL | SSL Certificate | ваш сертификат (Let's Encrypt или собственный) |
| | Force SSL, HTTP/2 Support, **HSTS Enabled** | включить |
| Advanced | Custom Nginx Configuration | `client_max_body_size 20m;` |

### 4.2. Портал правления
Так же, но домен `admin.rodnik.example.ru`, порт **`8082`**, а в Advanced:

```nginx
client_max_body_size 130m;
proxy_read_timeout 300s;
proxy_send_timeout 300s;
```

Без этого загрузка APK в портал будет обрываться ошибкой 413 (у NPM по умолчанию лимит 1 МБ).

### 4.3. Проверка
```bash
curl -sI https://rodnik.example.ru/            # 200, есть заголовок Content-Security-Policy
curl -s  https://rodnik.example.ru/api/health  # {"status":"ok"} (после первого деплоя)
```

### 4.4. Дополнительно: ограничить портал правления (по желанию)
**Access Lists → Add**: разрешите адреса правления/VPN (`Allow`), запретите остальным (`Deny all`). Затем в Proxy Host портала на вкладке Details выберите этот Access List. Сайт жителей (PWA) должен оставаться открытым.

## 5. GitLab

### 5.1. Переменные CI/CD
**Settings → CI/CD → Variables.** Каждую переменную заведите **дважды**: с областью (**Environment scope**) `test` и с областью `production`.

| Переменная | Тип | Значение |
|---|---|---|
| `SSH_PRIVATE_KEY` | **File** | содержимое `gsk-ci-test` (для `test`) / `gsk-ci-prod` (для `production`). В конце файла обязателен перевод строки |
| `SSH_KNOWN_HOSTS` | **File** | вывод `ssh-keyscan -p 22 <адрес сервера>` (закрепляет отпечаток сервера, защита от подмены) |
| `DEPLOY_HOST` | Variable | адрес сервера |
| `DEPLOY_PORT` | Variable | порт SSH, если не 22 (необязательно) |

Для `production`-переменных включите **Protect variable** и защитите ветку `main` (**Settings → Repository → Protected branches**: push — только владельцы/мейнтейнеры). Так боевой ключ доступен только пайплайнам защищённой ветки.

Закрытые ключи после добавления в GitLab удалите с компьютера или уберите в менеджер паролей.

### 5.2. Раннер
Нужен Runner с executor **Docker** и доступом в интернет (скачивает образы, npm-пакеты). Проект собирается без привилегированного режима.

### 5.3. Первый деплой
1. Отправьте код в ветку `develop`: пайплайн сам пройдёт `build → package → deploy_test`.
2. Откройте задачу `deploy_test` — в журнале видно каждый шаг деплоя на сервере.
3. На тестовом сервере создайте первого администратора:

```bash
sudo -u gsk-deploy /opt/gsk/bin/seed.sh
```

4. Войдите на `https://test-admin.rodnik.example.ru` телефоном и паролем, которые напечатал `setup.sh` (пароль также записан в `/etc/gsk/api.env`). Пароли пользователей меняет только администратор — через кнопку «Выдать пароль» в портале.
5. Сразу после входа система потребует **включить двухфакторную защиту**: поставьте на телефон приложение-аутентификатор (Яндекс Ключ, Google Authenticator, Microsoft Authenticator и т. п.), отсканируйте QR-код, введите код и **сохраните резервные коды** (распечатайте или уберите в менеджер паролей).
6. Удалите из `/etc/gsk/api.env` строку `SEED_ADMIN_PASSWORD=…` и перезапустите: `sudo systemctl restart gsk-api`.
7. Когда тест устроил — смержите `develop` в `main`, в пайплайне `main` нажмите **Run** у `deploy_prod`, затем так же выполните `seed.sh` на боевом.

## 6. Повседневная работа

| Задача | Как |
|---|---|
| Выкатить на тест | merge в `develop` — всё само |
| Выкатить на бой | merge в `main` → в пайплайне кнопка **Run** у `deploy_prod` |
| Откатить | в пайплайне нужной ветки запустить `rollback_test` / `rollback_prod` (вернёт предыдущий рабочий релиз) |
| Журнал API | `journalctl -u gsk-api -f` (на 100 строк назад: `-n 100`) |
| Состояние | `systemctl status gsk-api` |
| Перезапуск | `sudo systemctl restart gsk-api` |
| Изменить настройки | отредактировать `/etc/gsk/api.env`, затем перезапуск |
| Какая версия | `readlink /opt/gsk/current` |

Откат возвращает **код**, но не откатывает **миграции базы**. Поэтому миграции делайте обратно-совместимыми: сначала добавляйте новое (колонки, таблицы), и только в следующем релизе удаляйте старое. Перед каждой миграцией автоматически создаётся копия `…-pre-deploy.dump` (хранятся последние 10).

Хранится 5 последних релизов, остальные удаляются автоматически.

## 7. Резервные копии

**Что и когда.** Каждую ночь в 03:30 по Москве (`gsk-backup.timer`):
- дамп базы → `/var/backups/gsk/db/gsk-<дата>.dump` (хранится 14 дней), с контрольной суммой и проверкой читаемости;
- снимки загруженных файлов → `/var/backups/gsk/files/<дата>` (инкрементальные, 7 штук; повторяющиеся файлы не дублируются).

Плюс копия базы **перед каждым деплоем**.

**Проверка работы:**
```bash
systemctl list-timers gsk-backup.timer     # когда следующий запуск
cat /var/backups/gsk/last-backup.txt       # когда был последний успешный
sudo -u gsk bash -c 'set -a; . /etc/gsk/api.env; /opt/gsk/bin/backup.sh'   # запустить вручную
```

**PBS.** Каталог `/var/backups/gsk` находится внутри машины, поэтому ваш PBS забирает его вместе со всей системой. Убедитесь, что в задание PBS входит весь диск (или хотя бы `/var/backups/gsk`, `/var/lib/gsk`, `/etc/gsk`). Копии лежат рядом с данными — **полноценной защитой от потери сервера они становятся именно благодаря PBS**.

> В `/etc/gsk/api.env` лежат `JWT_ACCESS_SECRET`, пароль базы и ключи VAPID. Эти данные нужны для полного восстановления, но не входят в дамп. Храните копию `api.env` в менеджере паролей/сейфе. Потеря ключей VAPID означает, что браузерные push-подписки придётся оформить заново.

**Восстановление** (с остановкой сервиса; текущее состояние перед этим автоматически сохраняется с меткой `pre-restore`):

```bash
ls -lt /var/backups/gsk/db | head                          # выбрать дамп
sudo /opt/gsk/bin/restore.sh --db /var/backups/gsk/db/gsk-20261016-033012.dump \
       --files /var/backups/gsk/files/20261016-033012 --yes
```

Без `--yes` скрипт только покажет план. `--files` — необязательно (если нужны только данные базы).

> Хотя бы раз в квартал **проверяйте восстановление** на тестовом сервере: копия, которую не пробовали разворачивать, не гарантия.

## 8. Безопасность: что сделано и что остаётся

**Сделано:**
- сервис работает от отдельного пользователя без входа и оболочки, с ограничениями systemd (запись только в хранилище файлов, нет привилегий, фильтр системных вызовов);
- ключ CI может только выкатывать; никаких паролей CI на сервере; отпечаток сервера закреплён;
- API слушает только `127.0.0.1`; наружу — только через NPM по HTTPS; брандмауэр пропускает SSH (и порты сайтов только от NPM, если он на другой машине);
- заголовки безопасности (CSP, запрет встраивания, nosniff), ответы API не кэшируются;
- секреты вне репозитория, права 640; fail2ban на SSH; автоматические обновления безопасности Debian;
- зависимости на сервере ставятся без запуска чужих скриптов установки;
- двухфакторная защита (TOTP) обязательна для сотрудников правления на всех клиентах; секреты хранятся в базе в зашифрованном виде (ключ TOTP_ENC_KEY), резервные коды — только в виде хэшей, повторное использование кода исключено.

**Остаётся сделать вам / позже:**
- отключить вход по паролю в SSH;
- Firebase-ключ для push на Android;
- настроить почту (SMTP) — когда понадобятся чеки и письма;
- мониторинг доступности (например, Uptime Kuma, проверка `https://…/api/health`).

## 8а. Двухфакторная защита (2FA): эксплуатация

**Как работает.** После пароля сотрудник вводит 6-значный код из приложения на телефоне. Код меняется каждые 30 секунд. Есть 10 одноразовых **резервных кодов** на случай потери телефона. Пять неверных попыток (пароль или код) блокируют учётную запись до разблокировки администратором. Жителям 2FA не нужна.

**Ключ шифрования `TOTP_ENC_KEY`** создаётся `setup.sh` и лежит в `/etc/gsk/api.env`. **Не меняйте его после начала использования 2FA**: все секреты в базе зашифрованы им, при смене у всех сотрудников 2FA перестанет работать (придётся сбрасывать каждому). Храните копию `api.env` в сейфе.

**Если сотрудник потерял телефон**
1. У него есть резервные коды → он входит по резервному коду и в разделе «Безопасность» выпускает новые (или настраивает защиту заново: сначала сброс, см. п. 2).
2. Резервных кодов нет → другой сотрудник с правом «Выдача паролей» открывает «Пользователи» и нажимает значок щита «Сбросить 2FA». Сессии пользователя завершаются, при следующем входе он настроит защиту заново.
3. **Потеряны телефон и коды у единственного администратора** → сброс с сервера:

```bash
sudo -u gsk-deploy /opt/gsk/bin/reset-2fa.sh 9001112233
```

Действие записывается в журнал (автор `server-cli`).

**Политика.** Администратор может отключить требование (Безопасность → «Требовать двухфакторную защиту»), но по умолчанию оно включено. Если требование включено, а у сотрудника защиты ещё нет, ему доступна только настройка (проверка на сервере, обойти её входом через другой клиент нельзя).

**Журнал.** В журнале действий видны события `auth.2fa.*` (запрос кода, неверный код, использование резервного кода, включение, перевыпуск кодов) и `user.2fa.reset`.

## 9. Если что-то пошло не так

| Симптом | Причина и решение |
|---|---|
| Задача `deploy_*` красная: «API не ответил» | Смотрите `journalctl -u gsk-api -n 100` на сервере: чаще всего неверное значение в `/etc/gsk/api.env` или миграция. Предыдущий релиз уже возвращён автоматически |
| `Permission denied (publickey)` в CI | Не тот ключ в `SSH_PRIVATE_KEY` или нет перевода строки в конце файла; проверьте строку в `/home/gsk-deploy/.ssh/authorized_keys` |
| `Host key verification failed` | В `SSH_KNOWN_HOSTS` не тот сервер/порт — выполните `ssh-keyscan` заново |
| В NPM ошибка 502 | NPM не достаёт до `8081/8082`: проверьте IP/порт, `systemctl status nginx`, у ufw — `--npm-ip` |
| Загрузка APK: `413 Request Entity Too Large` | В Advanced проксихоста портала нет `client_max_body_size 130m;` |
| Браузер: ошибка CORS | Домен не указан в `CORS_ORIGINS` в `/etc/gsk/api.env` (для Android нужен `https://localhost`) |
| В журналах у всех клиентов один IP | Неверное `TRUST_PROXY_HOPS` (при схеме NPM → nginx → API должно быть `2`) |
| Миграция упала при деплое | Деплой остановился до переключения — прежняя версия работает. Исправьте миграцию; при необходимости базу можно вернуть из `…-pre-deploy.dump` через `restore.sh` |
| Нужно вручную выкатить без GitLab | `cat release.tar.gz \| ssh -i ключ gsk-deploy@сервер <ид-релиза>` (архив собирает `scripts/package-release.sh`) |

## 10. Состав файлов деплоя

```
.gitlab-ci.yml                     конвейер: build → package → deploy (test авто, prod вручную) + rollback
scripts/package-release.sh         упаковка release.tar.gz
deploy/server/
  setup.sh                         первичная настройка сервера
  bin/deploy-receive.sh            приём релиза, миграции, переключение, проверка, откат
  bin/backup.sh  restore.sh        резервная копия и восстановление
  bin/seed.sh                      создание первого администратора
  bin/reset-2fa.sh                 аварийный сброс 2FA пользователю
  systemd/gsk-api.service          сервис API (с ограничениями безопасности)
  systemd/gsk-backup.{service,timer}  ночной бэкап
  nginx/…                          внутренние сайты (PWA :8081, портал :8082), заголовки безопасности
  env/api.env.template             шаблон /etc/gsk/api.env
```

## Приложение: Runner без Docker (executor `shell`)

Само приложение Docker не использует (systemd + nginx). Docker нужен только Runner'у для сборки в чистом контейнере. Если Docker не нужен, зарегистрируйте Runner с executor **shell** на любой Linux-машине (можно на самом сервере ГСК или отдельной):

```bash
# зависимости сборки (Debian): Node.js 22 (nodesource), git, openssh-client, tar, build-essential
sudo apt-get install -y git openssh-client tar build-essential curl
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo bash - && sudo apt-get install -y nodejs
curl -fsSL https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.deb.sh | sudo bash
sudo apt-get install -y gitlab-runner
sudo gitlab-runner register --non-interactive --url http://GITLAB --token glrt-ТОКЕН --executor shell
```

Строки `image:` в `.gitlab-ci.yml` при shell-executor игнорируются, `openssh-client` берётся из системы. Сборка идёт от пользователя `gitlab-runner` в его каталоге `builds`; ему нужен доступ в интернет (npm). Если Runner стоит на самом сервере ГСК, `DEPLOY_HOST` может быть `127.0.0.1` (или адрес сервера), а SSH-ключ для CI — тот же `gsk-ci-test`.
